# BodyBuilder browser checks

The fixture browser suite uses an explicit asynchronous, browser-local mock API. Each fixture test starts in its own browser context, freezes the calendar to 9 October 2026 in Asia/Singapore, and records uncaught page errors. The live suite under `tests/live/` uses real Go and PostgreSQL through the same-origin SvelteKit proxy, with unique synthetic accounts and separate browser contexts.

The final nutrition milestone passed 70 fixture development checks, 26 live development checks, two fixture production PWA checks, and twelve live production nutrition/offline checks in mobile Chromium/WebKit: 110 browser checks. All four suites were run sequentially after the shared sheet focus fix. Live cases use real Go/PostgreSQL; fixture checks remain separate. Exact commands, coverage, and remaining external/device limits are in the [live verification report](../../docs/LIVE_VERIFICATION.md).

- `npm run test:ui` runs mobile Chromium and WebKit in `PUBLIC_API_MODE=mock` against Vite on port 5175. The fixture helper fails if the browser calls the live `/api/v1/` API.
- `npm run test:ui:production` builds the mock frontend and runs the fixture suite plus its service-worker/offline check against preview on port 4175.
- `npm run test:ui:production -- tests/pwa.spec.ts --reporter=list --max-failures=2` builds the mock frontend and runs just the two fixture production PWA cases.
- `npm run test:live` uses `playwright.live.config.ts` with `PUBLIC_API_MODE=live` on port 5176. Set `BACKEND_API_URL` to the isolated E2E Go service; the default is `http://127.0.0.1:8082`. The real Go service and PostgreSQL must already be running.
- `npm run test:live:production` builds the live frontend on port 4176 and also runs durable offline replay against PostgreSQL. The verified production selection is `npm run test:live:production -- tests/live/nutrition.spec.ts tests/live/offline.spec.ts --reporter=list --max-failures=2` (twelve checks). It does not claim a full production rerun of every live development scenario.
- `npx playwright test tests/visuals.spec.ts` captures the five tabs, workout preview, and active workout at 393 × 852. Captures are attached to the Playwright report. They are review artifacts, not approved golden baselines.
- `npx playwright test tests/sheets.spec.ts` checks expansion, collapse, dismissal, retained unsaved notes, small-drag snap-back, reopening, keyboard resizing, close controls, and focus restoration. Both engines use real mouse input; Chromium additionally uses native touch input to check expansion and touch cancellation. Form scrolling uses a real wheel in Chromium and scrolling a lower control into view in mobile WebKit, whose automation API lacks mouse-wheel support.
- `npx playwright show-report` opens the last HTML report. Failure traces, screenshots, and videos are retained under `test-results/`.

Browser binaries must match the installed Playwright version. Install them with `npx playwright install chromium webkit` if the local cache does not already contain them.

GitHub Actions runs the four verified suite selections with separate HTML reports and failure artifacts. `python3 scripts/run_live_ui_checks.py` from the repository root owns the isolated API lifecycle for both live selections, including schema cleanup. See [CI setup and reproduction](../../docs/CI.md) for Linux prerequisites, executable paths, and local commands.

Live provider-error cases require `E2E_ADMIN_EMAIL` and `E2E_ADMIN_PASSWORD` for a synthetic administrator in the isolated E2E schema. Missing values fail the test. Configure every E2E provider URL to a local error stub so the fake test key cannot reach a paid service. No test uses Playwright route mocks for API responses. Dedicated mock/live ports prevent cached fixture data and service workers from mixing between modes.

The mocked failure hook is consumed by one request: `localStorage.setItem('bodybuilder.preview.fail-next', 'saveCheckIn')`. A failed mutation must leave the editor draft open and preserve the previous persisted snapshot.

Production offline cases use a separate HTTP proxy on a random localhost port for each browser context. After the service worker controls the page, the proxy keeps listening but destroys incoming transport sockets and stops forwarding requests. An uncached fetch must reject before checking cached shell reloads and edits. This disconnects service-worker requests as well as page requests without relying on browser offline emulation. Fixture cleanup closes the proxy even if an assertion fails. Cache checks ensure no `/api/` responses are stored. The mock PWA case checks local preview persistence; the live PWA case additionally checks unchanged server state during the outage, durable per-user IndexedDB operation IDs/base revisions across reload, and replay once into real PostgreSQL after reconnecting.

The browser checks cover private mock-account switching, stale-history draft isolation, five-tab navigation and narrow-screen geometry, calendar rollover, workout logging and rest recovery, nutrition edits and dated copying, daily check-in upserts, lesson-library management, and explicit review before saving simulated meal estimates. Screenshots are captured for visual review; no comparison to approved golden images is claimed.

The live browser cases add real registration/login/logout, cross-device synchronization, explicit HTTP409 keep/discard decisions, private cached-account isolation, empty account initialization, CRUD persistence, and real no-key/upstream error UI. `live/workouts.spec.ts` also pauses and then forwards an unchanged real session-save request while tapping effort: the control must stay in place, its picker must open, and reps/effort must persist in PostgreSQL. The fixture notification regression in `checkins.spec.ts` sends a native pointer click where a visible save notification overlaps the check-in card; the editor must open with its saved notes. These two regressions add four cases to the previous nutrition milestone, bringing that CI selection to 114 browser cases (72 fixture development cases). Provider response formats and encrypted settings are verified by separate Go tests using local HTTP stubs and PostgreSQL.

`nutrition-calculation.spec.ts` verifies required personal choices, previews from shared golden fixtures, cancellation without persistence, explicit apply, manual override provenance, later effective dates, no automatic changes after daily weight entry, exact kilogram preservation when displaying pounds, edited-pound conversion, invalid allocations, and account-draft isolation. The separate `npm run test:nutrition` script checks all eight common Go/TypeScript golden fixtures plus runtime input/allocation validation without relying on browser UI.

`live/nutrition.spec.ts` verifies the authenticated read-only calculator response, unchanged server revision before apply/cancel, real cross-device provenance and manual history, private inputs, genuine USDA SR Legacy banana nutrients and attribution, two-serving precision, real unavailable-upstream errors, and the absence of assistant traffic from calculation or database search. It checks that opening autofocus preserves a search field already being typed in, then tests keyboard submission and the visible Search button. Its offline case uses the real transport proxy while the UI is already loaded: a pending weight change cannot replace the acknowledged calculator prefill, the identical local preview stays unsaved, and explicit Apply creates a durable revisioned operation that replays into PostgreSQL. These are genuine local database records and API responses; no paid AI call or response mocking is used.

The live food-search case also verifies that the search icon, input, and explicit Search button remain aligned on one compact row at 320px, 393px, and 1024px viewport widths. It checks containment and a minimum 44px Search tap target, then attaches a settled phone screenshot for review. This regression reproduces the dialog form rule that previously stacked the controls vertically; the existing nutrition fixture cases cover the remaining manual food and target forms.

`programs.spec.ts` adds five starter-program scenarios per engine for PHUL, PPL, barbell 5×5, glute focus and dumbbell full body. It verifies source/adaptation links, private copies, preserved prescriptions, explicit scheduling, real local images and technique guides, and reload persistence. Timed bridge holds use a seconds input and omit the weight column. The expanded live workout case checks every new plan through Go/PostgreSQL, source-note preservation after editing, second-device sync, and a saved 20-second bridge hold. The configured CI selection now has 126 browser cases (82 fixture development, 30 live development, two fixture production PWA, twelve live production nutrition/offline). Verification for this program-library change passed 26 targeted checks: 18 fixture program/workout, six live workout, and two production PWA checks, all with zero retries. Backend race/vet checks, all 12 mock client checks, catalogue/asset parity and clean Svelte diagnostics also passed. See [the execution plan](../../PROGRAM_LIBRARY_PLAN.md) for sources, mappings and exact scope.

These checks do not verify external provider availability, actual paid LLM responses, or installation on physical iPhone and Android devices. Native camera permissions, background execution, OS notifications, and installed-PWA behavior still require device testing.
